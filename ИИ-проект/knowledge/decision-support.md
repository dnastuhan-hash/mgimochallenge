# Поддержка решений после выбора

Решение без сохранённых оснований через квартал превращается в «так исторически сложилось». Агент хранит:

| Поле записи решения (`sfp decision add`) | Зачем |
|---|---|
| `title`, `choice` | Что решили и какой вариант выбрали (и какие отвергли) |
| `owner`, `decided_by` | Кто отвечает за исполнение, кто принял |
| `grounds` | Утверждения C-…, на которых решение держится |
| `metric` | Показатели, по которым судим об успехе (с порогом) |
| `review_by` | Дата обязательного пересмотра |
| `trigger` | Условия внепланового пересмотра («если доля перебоев из-за неоплаты > 50 %») |
| `commitments` | Обязательства: что, кто, к какому сроку (`sfp decision commit`) |

## Что агент делает в начале каждой сессии на шаге 11
1. `./sfp check` — находит решения с устаревшими основаниями, наступившие сроки пересмотра, просроченные обязательства.
2. `./sfp decision list` — показывает руководителю, **что решать сейчас**: сроки, триггеры, обязательства.
3. Если основание заменено (`supersede`) — `./sfp impact C-…` и предложение: сохранить решение / изменить / пересмотреть.

## Подсказки «что решать сейчас»
- Наступил `review_by` → подготовить короткую записку: что изменилось с момента решения, выполнено ли обязательство,
  какие основания устарели, варианты (продолжить / изменить / остановить).
- Сработал триггер → то же, но с указанием, какое наблюдение его вызвало.
- Обязательство просрочено → кто ответственный, что блокирует, как это меняет прогноз.
