# План проверки (пилот)

## Обязательные элементы
| Элемент | Вопрос |
|---|---|
| Ожидаемое изменение | Какая метрика, числитель/знаменатель, единица, на сколько (минимально важное для клиента) |
| Сравнение | С чем сравниваем: случайная группа обычного обслуживания (лучше) или обоснованно сопоставимая |
| Кого включать | Условия, без которых помочь невозможно (совместимость тарифа, согласие, свободный остаток…) |
| Первый подходящий случай | Событие, с которого начинается наблюдение; одинаково регистрируется в обеих группах |
| Срок наблюдения | Одинаковый для обеих групп; набор + наблюдение за последними участниками |
| Размер выборки | Из базовой частоты, минимального эффекта, α и мощности |
| Темп набора | Хватит ли подходящих случаев за отведённое время |
| Нежелательные последствия | Ложные сигналы, двойные списания, перебой у другого участника; стоп-условия |
| Порог решения | Заранее: какое улучшение оправдает расширение, какой разброс оценки допустим |

## Единица рандомизации
Если участники делят пакет, действие одного меняет остаток другого → назначай **всей семье** один вариант.
Для нескольких номеров одного владельца — распределение по владельцам. Укажи, какие номера в расчёте и как учтёшь
повторные события.

## Анализ
- Начинай отсчёт в момент подходящего события; наблюдай обе группы одинаково долго.
- **Считай всех включённых** (intent-to-treat), включая не открывших сообщение. Подсчёт только откликнувшихся
  создаёт видимость пользы (их исходная готовность помочь выше).
- Проверь до запуска, что сведения об ограничениях, оплате и результате операции одинаково доступны в обеих группах.

## Размер выборки (две доли)
`n на группу = (z_{1−α/2}·√(2p̄(1−p̄)) + z_{1−β}·√(p1(1−p1)+p2(1−p2)))² / (p1−p2)²`
Пример: 12 % → 9 %, α = 0,05, мощность 0,8 → ≈ 1 630 групп на вариант. Скрипт: `tools/calc/sample_size.py`.
При рандомизации по семьям и метрике по номерам учитывай эффект дизайна `1 + (m − 1)·ICC`.

## Темп набора
Нужно N разных групп за T недель → в среднем N/T **впервые подходящих** групп в неделю. Число подключённых на конец
года само по себе не показывает, сколько из них столкнутся с нужной ситуацией в период набора.
Если не хватает: удлинить набор, принять больший минимальный эффект, расширить критерии, сменить метрику на
более частую (с оговоркой, что она ближе к процессу, чем к пользе).

## Действия по результату
- Польза достаточно велика и услуга работает надёжно → следующий охват; **сохрани группу сравнения** среди новых
  клиентов, у которых подходящий случай произошёл впервые.
- Наблюдений мало → сколько ещё нужно и когда вернуться к решению.
- Улучшение замечено только после анализа в одном подсегменте (тариф) → это новая гипотеза, проверь на новых клиентах.
- Ошибки оплаты/доступа → сначала разбор с владельцем системы.
- За отведённое время проверяемо только понимание или исполнение операции → так и сформулируй вывод и предложи
  отдельную проверку влияния на связь.
