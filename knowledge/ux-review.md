# Разбор интерфейсов и пути клиента

## Принцип: только то, что видно
Каждое замечание привязано к материалу: «скриншот S-007, экран 2, кнопка "Поделиться" ниже сгиба». Если вывод
требует того, чего на материале нет (поведение после нажатия, тексты ошибок), — это гипотеза «проверить в прототипе».

## Порядок
1. Инвентарь материала: какие экраны/шаги есть, каких нет (пробелы пути).
2. Путь по ролям: организатор / участник / плательщик / владелец номеров — шаги, решения, точки отказа.
3. Для каждого шага: что человек должен понять → видно ли это на экране → что мешает (композиция, иерархия,
   терминология, количество действий, состояние ошибки/ожидания).
4. Критические состояния: ожидание подтверждения операции, ошибка, повторное нажатие, отзыв согласия.
5. Итог: 3–5 проблем по тяжести (блокирует / замедляет / косметика) с привязкой и предложением проверки.

## Проверка удобства (для пилота)
Предложи людям решить одну и ту же задачу привычным и новым способом; меняй порядок между участниками при
сравнении времени. Наблюдай: кто справился без подсказки, где возникла ошибка, сколько заняло действие.

## Если материала нет
Построй путь из текстового описания (бриф) и явно пометь: «путь реконструирован из описания, интерфейс не
анализировался».
